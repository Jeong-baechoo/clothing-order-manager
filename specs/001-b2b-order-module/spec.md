# B2B 발주 모듈 — 기능 명세 (Spec)

- 상태: Draft v1
- 작성일: 2026-06-13
- 관련 문서: [plan.md](./plan.md) (기술 설계), [tasks.md](./tasks.md) (작업 분해)

> SDD 원칙: 이 문서는 **무엇을(What) / 왜(Why)**만 다룬다. 테이블/SQL 등 구현 방법은 `plan.md`에 둔다.

---

## 1. 개요 (Why)

의류 + DTF 프린팅 단일 매장의 내부 주문관리 시스템에, **외부 발주처(거래처/딜러)가 로그인해 우리 카탈로그에서 직접 도매 발주**하는 B2B 포털을 **별도 모듈**로 추가한다. 기존 고객주문(프린팅) 관리 흐름은 변경하지 않는다.

## 2. 목표 / 비목표

**목표 (MVP)**
- 관리자가 발주처 계정을 발급하고, 발주처별 전용 제품과 변형(사이즈·색상)별 재고를 관리한다.
- 발주처가 로그인해 **자기에게 배정된 제품의 재고만** 보고 발주(신청)한다.
- 관리자가 발주를 접수(확정)할 때 재고가 원자적으로 차감되어 **초과판매가 발생하지 않는다.**
- 발주 상태를 신청 → 확정 → 출고 → 완료로 진행하고, 취소 시 재고를 복원한다.

**비목표 (MVP 제외, 후속)**
- 결제 / 여신(외상)
- 배송 / 송장 연동 (출고는 상태값으로만 추적)
- 최소발주수량(MOQ), 박스 단위 제약
- 발주처 셀프 가입
- 발주처별 차등 단가
- 멀티매장(테넌트) 일반화

## 3. 사용자 역할

| 역할 | 설명 | 권한 |
|------|------|------|
| **관리자(admin)** | 우리 매장 운영자 | 전체 (발주처·제품·재고·발주 관리) |
| **발주처(buyer)** | 우리한테 발주하는 외부 업체 | 자기 배정 제품/재고 조회, 자기 발주 생성·조회만 |

발주처 ≠ 기존 `companies`(우리가 사입하는 공급처). 둘은 별개 개념이다.

## 4. 사용자 스토리 & 인수 조건

### US-1. 발주처 계정 발급 (관리자)
관리자는 발주처를 등록하고 로그인 계정(이메일)을 발급한다. 발주처당 계정은 1개.
- **Given** 관리자로 로그인한 상태에서
- **When** 발주처 이름·로그인 이메일을 입력해 등록하면
- **Then** 발주처가 생성되고 해당 이메일로 로그인 가능한 계정이 1개 연결된다.

### US-2. 제품을 발주처에 전용 배정 (관리자)
관리자는 제품을 특정 발주처에 배정한다(전용). 배정 안 된 제품은 기존 고객주문용으로 남는다.
- **Given** 발주처와 제품이 존재할 때
- **When** 제품에 발주처를 배정하면
- **Then** 그 제품은 해당 발주처에게만 노출/발주 가능해진다.

### US-3. 변형 재고 등록 (관리자)
관리자는 제품의 사이즈·색상 조합별 재고 수량과 비고를 등록/수정한다.
- **Given** 제품이 존재할 때
- **When** (사이즈, 색상, 수량, 비고)를 입력하면
- **Then** 해당 변형의 재고가 저장되고, 같은 (제품·사이즈·색상)은 중복 생성되지 않는다.

### US-4. 발주처 로그인 & 카탈로그 조회 (발주처)
- **Given** 발급받은 계정으로 로그인한 발주처가
- **When** 포털에 접속하면
- **Then** **자기에게 배정된 제품과 그 변형 재고만** 보인다(다른 발주처/고객주문 제품은 안 보임).

### US-5. 발주 생성 (발주처)
- **Given** 로그인한 발주처가 카탈로그에서
- **When** 변형(사이즈·색상)별 수량을 담아 발주를 신청하면
- **Then** 상태 `신청`의 발주가 생성되고, 발주 라인에 제품명·단가(도매가)가 스냅샷으로 저장된다.
- 신청 수량은 **현재 재고를 초과할 수 없다**(초과 시 신청 차단). 단, 이 시점에 재고는 차감/예약되지 않는다.

### US-6. 발주 접수 & 재고 차감 (관리자)
- **Given** 신청 상태의 발주가 있을 때
- **When** 관리자가 접수(확정)하면
- **Then** 각 라인의 재고를 **원자적으로 재검증 후 차감**하고 상태를 `확정`으로 바꾼다. 재고 부족 라인이 하나라도 있으면 **접수 전체가 거부**되고 차감은 일어나지 않는다.

### US-7. 발주 진행 (출고/완료) (관리자)
- **When** 관리자가 확정 → 출고 → 완료로 상태를 진행하면
- **Then** 상태만 변경된다(재고 추가 변동 없음).

### US-8. 발주 취소 & 재고 복원 (관리자)
- **When** 관리자가 발주를 취소하면
- **Then** 이미 차감된 발주(확정 이후)면 재고를 **복원**하고, 신청 단계 발주면 차감이 없었으므로 상태만 `취소`로 바꾼다.

### US-9. 데이터 격리 (시스템)
- **Given** 어떤 발주처가
- **When** API/직접 쿼리로 다른 발주처의 제품·재고·발주를 조회·수정 시도하면
- **Then** DB(RLS) 레벨에서 차단되어 접근할 수 없다.

## 5. 기능 요구사항 (FR)

- **FR-1** 발주처는 이름과 고유 로그인 이메일을 가지며, 활성/비활성 상태를 가진다.
- **FR-2** 발주처당 인증 계정은 **정확히 1개**다.
- **FR-3** 제품은 0~1개의 발주처에 배정될 수 있다(배정 없으면 고객주문용).
- **FR-4** 재고는 (제품, 사이즈, 색상) 단위로 관리되며 수량은 **0 이상**이다.
- **FR-5** 발주 상태는 `신청 → 확정 → 출고 → 완료` 및 `취소`만 허용한다.
- **FR-6** 발주 라인은 수량(>0), 단가·제품명 스냅샷을 가진다.
- **FR-7** 재고 차감은 **접수(확정) 시점**에 단일 트랜잭션으로 검증+차감한다.
- **FR-8** 재고가 부족하면 접수가 거부되고 부분 차감은 발생하지 않는다.
- **FR-9** 확정 이후 취소 시 재고를 복원한다.
- **FR-10** 발주처는 자기 배정 제품·재고·발주만 조회/생성 가능하다(RLS 강제).
- **FR-11** 관리자는 전체 발주처·제품·재고·발주를 관리할 수 있다.

## 6. 엣지 케이스

| 상황 | 기대 동작 |
|------|-----------|
| 두 발주처가 같은 재고를 동시 신청 | 둘 다 신청 가능(예약 없음). 접수 순서대로 차감, 나중 접수가 재고 부족이면 거부 |
| 신청 후 접수 전에 재고가 0이 됨 | 접수 시 재검증에서 거부 |
| 발주처 비활성화 | 로그인/발주 불가, 기존 발주 이력은 유지 |
| 제품의 발주처 배정 해제 | 이후 그 발주처에 노출 안 됨. 과거 발주 라인은 스냅샷으로 보존 |
| 재고 0인 변형 | 카탈로그에 품절 표시, 신청 불가 |
| 발주 라인 일부만 재고 부족 | 접수 전체 거부(부분 접수 없음, MVP) |

## 7. 범위 밖 (명시적 비포함)
결제·여신, 배송/송장, MOQ, 부분 접수/분할 출고, 발주처 셀프가입, 차등단가, 알림(이메일/SMS)은 MVP에 포함하지 않는다. 후속 단계에서 별도 스펙으로 다룬다.
